# Triggers

**Triggers** are listeners that watch for changes on your entities and execute custom logic when those changes occur. They enable you to automatically respond to data modifications in your application by configuring actions that execute when specific events happen, such as the **creation**, **update**, or **deletion** of records.

Triggers provide a flexible way to enforce business logic, automate workflows, or integrate with external services without manual intervention.

        ## Creating a Trigger

        ![Create Trigger](/images/bsh-egnine/triggers/create-trigger.png)

        | Field      | Description                                                                  |
        |------------|------------------------------------------------------------------------------|
        | Name       | The unique identifier for the trigger.                                       |
        | Label      | A human-readable name for the trigger.       |
        | Entity     | The entity to monitor for changes.                                           |
        | Trigger On | The event type that activates the trigger: `Insert`, `Update`, or `Delete`. |
        | Enabled    | Whether the trigger is currently active.                                     |
        | Criteria   | Conditions that must be met for the trigger to fire.                         |
        | Lookups    | Optional searches that load related records before trigger events run.       |
        | Events     | Actions to execute when the trigger conditions are met.                  |

        ## Lookups

        ![Lookups](/images/bsh-egnine/triggers/lookup-popup.png)

        **Lookups** let a trigger fetch related entity records with a standard BSH search object before any of its events run. Each lookup runs only after the trigger-level **criteria** passes. Results are grouped under a name you choose and exposed as the `lookups` object in event criteria and in event **input**, **output**, and **failed** JSON.

        Lookups execute searches with system access so related data can be loaded reliably; restrict what you fetch with `fields` and filters, and avoid exposing sensitive lookup fields in logs or downstream outputs.

        Configure lookups in the trigger form under **Lookups**. Each entry has:

        | Field  | Description |
        |--------|-------------|
        | Key    | Name used to read the result (for example `user`, `relatedOrders`). |
        | Search | A BSH search object (`entity`, `filters`, `fields`, `sort`, `pagination`, etc.). Values support `${}` and `$js()` like other trigger JSON. |

        When the trigger fires, the engine resolves each lookup’s `search` against the current trigger context (`payload`, `entity`, `user`, and `variables`), runs the search, and stores matching rows as a **JSON array** at `lookups.<key>`. If a search fails or returns no rows, that key is omitted from `lookups`.

        <Callout type="info">
            Lookups are **not** available in trigger-level criteria; they run only after that criteria succeeds. Use them in **event** criteria and in event JSON configurations.
        </Callout>

        **Example lookup configuration:**

        ```json
        [
            {
                "key": "assignee",
                "search": {
                    "entity": "User",
                    "filters": [
                        {
                            "field": "id",
                            "operator": "eq",
                            "value": "${payload.assigneeId}"
                        }
                    ],
                    "fields": ["id", "email", "profile"]
                }
            },
            {
                "key": "openTasks",
                "search": {
                    "entity": "Task",
                    "filters": [
                        {
                            "field": "orderId",
                            "operator": "eq",
                            "value": "${payload.id}"
                        },
                        {
                            "field": "status",
                            "operator": "eq",
                            "value": "OPEN"
                        }
                    ]
                }
            }
        ]
        ```

        **Using lookup results in event criteria:**

        ```js
        lookups.openTasks.length > 0

        lookups.assignee[0]?.email?.endsWith('@company.com')
        ```

        **Using lookup results in event input:**

        ```json
        {
            "taskCount": "$js(lookups.openTasks.length)",
            "notifyEmail": "${lookups.assignee.0.email}",
            "orderId": "${payload.id}"
        }
        ```

        ## Trigger Events

        A Trigger can have multiple events, each of which can be configured independently.<br/>
        Each event represents a specific action to execute when the trigger fires, such as calling a function, updating
        related records, or integrating with external services.

        ![Trigger Events](/images/bsh-egnine/triggers/trigger-events.png)

        | Event         | Description                                                    |
        |---------------|----------------------------------------------------------------|
        | Name          | The identifier for the event.                                  |
        | Function      | The function to execute when the event is triggered.           |
        | Enabled       | Whether this specific event is active.                         |
        | Target Entity | The entity that the event will update.                         |
        | Criteria      | Additional conditions specific to this event.                  |
        | Input         | Input parameters passed to the function.                       |
        | Output        | Output configuration for the function result.                  |
        | Failed        | Configuration for handling event failures.                     |
        | infiniteLoop  | Configuration to prevent infinite loop scenarios.              |

        <Callout type="info">
            `Target Entity` is used only when the event needs to perform update on an entity.
        </Callout>

        ## Criteria

        Criteria are JavaScript expressions that determine whether a trigger or event should execute. You have access to the following variables in your criteria expressions:

        ```js
        const payload = {}   // The record that triggered the event
        const entity = {}    // The BSH entity definition
        const user = {       // The user triggered the event
            type: "User|ApiKey",
            userId: "string",
            email: "string",
            profile: {}
        }
        const variables = {} // Engine configuration variables (when configured)
        const lookups = {}   // Lookup results — event criteria only; keys map to arrays of records
        ```

        <Callout>
            **Criteria** is a JavaScript expression that evaluates to a boolean value. For example: `payload.status == 'NEW'` or `user.email.includes('@company.com')`. The `lookups` object is available in **event** criteria only, after trigger lookups have been resolved.
        </Callout>

        **Example:**
        ```js
        // Check if status changed to active
        payload.status == 'ACTIVE'

        // Check if user is from a specific domain
        user.email.endsWith('@company.com')

        // Check if amount is above threshold
        payload.amount > 1000

        // Complex condition
        payload.status == 'NEW' && user.type == 'User'
        ```

        ## Event JSON Configurations

        The `input`, `output`, and `failed` fields are JSON objects that allow you to customize the data flow through your trigger events. Here are the variables available in each context:

        <Tabs items={['Input', 'Output', 'Failed']}>
            <Tabs.Tab>
                The input JSON defines what data is passed to your trigger function.

                ```json
                {
                    "payload": {},
                    "entity": {},
                    "user": {
                        "type": "User|ApiKey",
                        "userId": "string",
                        "email": "string",
                        "profile": {}
                    },
                    "variables": {},
                    "lookups": {}
                }
                ```

                **Example:**
                ```json
                {
                    "recordId": "${payload.id}",
                    "status": "${payload.status}",
                    "triggeredBy": "${user.email}",
                    "entityName": "${entity.name}",
                    "openTaskCount": "$js(lookups.openTasks?.length ?? 0)"
                }
                ```
            </Tabs.Tab>

            <Tabs.Tab>
                The output JSON defines how to process the function's result. this json will be inserted to the `target entity` if defined.

                ```json
                {
                    "payload": {},
                    "entity": {},
                    "user": {
                        "type": "User|ApiKey",
                        "userId": "string",
                        "email": "string",
                        "profile": {}
                    },
                    "variables": {},
                    "lookups": {},
                    "result": {},
                    "instance": {},
                    "error": {}
                }
                ```

                **Example:**
                ```json
                {
                    "success": true,
                    "updatedRecord": "$js(result.data)",
                    "executionTime": "$js(new Date().toISOString())"
                }
                ```
            </Tabs.Tab>

            <Tabs.Tab>
                The failed JSON defines how to handle errors when the function fails.

                ```json
                {
                    "payload": {},
                    "entity": {},
                    "user": {
                        "type": "User|ApiKey",
                        "userId": "string",
                        "email": "string",
                        "profile": {}
                    },
                    "variables": {},
                    "lookups": {},
                    "result": {},
                    "instance": {},
                    "error": {}
                }
                ```

                **Example:**
                ```json
                {
                    "errorMessage": "${error.message}",
                    "failedRecordId": "${payload.id}",
                    "timestamp": "$js(new Date().toISOString())",
                    "notifyAdmin": true
                }
                ```
            </Tabs.Tab>

        ### How to access the variable

        You can access variables in JSON configurations using two methods:

        <Callout type="info">
            **String Interpolation**: Use `${}` to embed variable values directly
            ```json
            "recordId": "${payload.id}"
            ```

            **JavaScript Expressions**: Use `$js()` to execute JavaScript code
            ```json
            "total": "$js(payload.quantity * payload.price)",
            "isValid": "$js(payload.amount > 0 && payload.status === 'PENDING')"
            ```
        </Callout>

        ## Infinite Loop Prevention

        BSHEngine includes built-in protection against infinite loops that can occur when triggers create cascading updates.

        The engine detects and prevents infinite loops using two mechanisms:

        1. **Payload Change Detection**: The trigger stops executing if the payload hasn't changed since the last execution.

        2. **Maximum Depth Limit**: When a trigger repeatedly updates the same entity, the engine uses the `infiniteLoop.maxDeep` setting to limit how many times the trigger can execute before stopping.

        <Callout type="error">
            Make sure all times to double check the trigger criteria and outputs to ensure they don't create infinite loops.
        </Callout>

        <Callout type="warning">
            If you're experiencing issues with triggers stopping unexpectedly, check if you've created a circular trigger dependency. Adjust the `maxDeep` value carefully to balance protection with legitimate use cases.
        </Callout>

        ## Payload Sanitizer

        The **sanitizer** is a built-in safety feature that lets you automatically remove or mask sensitive fields from the payload before any trigger log is recorded. This helps protect confidential data, such as user emails, credit card numbers, or authentication tokens, from being leaked to logs where they might be accessed by unauthorized users.

        ![Sanitizer](/images/bsh-egnine/triggers/sanitize-trigger.png)

        <Callout type="info">
            Set up the sanitizer in your trigger configuration by specifying which keys should be masked. Only non-sensitive fields will be stored in the logs, helping you stay compliant with internal security policies and privacy regulations.
        </Callout>

        **Example use cases:**
        - Hiding fields like `password`, `apiKey`, or `ssn` in audit logs.
        - Obscuring personally identifiable information (PII) for compliance purposes.
        - Ensuring log outputs are safe to be accessed by support or development teams.
   

        ## Trigger Functions

        Functions are built-in logical blocks that you can use to execute custom logic within your triggers. These functions provide pre-configured operations that can be called when trigger events fire.

        For a complete list of available trigger functions and their parameters, refer to the [Trigger Functions](/docs/bsh-engine/triggers/functions) documentation.

        ## Best Practices
        1. **Be Specific with Criteria**: Write precise criteria to avoid unnecessary trigger executions.
        2. **Scope Lookups**: Fetch only the fields and rows events need; use filters tied to `payload` values to keep searches small.
        3. **Handle Failures Gracefully**: Always configure the `failed` JSON to capture and handle errors appropriately.
        4. **Avoid Circular Dependencies**: Design your trigger logic to prevent one trigger from creating conditions that fire another trigger in a loop.
        5. **Test Thoroughly**: Test triggers with various scenarios before enabling them in production.
        6. **Use Meaningful Names**: Give triggers and events descriptive names that explain their purpose.
        7. **Use Payload Sanitizer**: Configure the sanitizer to mask sensitive fields from the payload before it is stored to the logs.

        ## Common Use Cases
        - **Notifications**: Send alerts when specific conditions are met
        - **Data Enrichment**: Automatically populate related fields
        - **Related data**: Load users, line items, or child records via lookups before running events
        - **Workflow Automation**: Trigger downstream processes based on data changes
        - **Integration**: Sync data with external systems
        - ...

        ## API Reference

        ### BshTrigger Type

        ```ts
        export type BshTriggerLookup = {
            key: string
            search: BshSearch
        }

        export type BshTrigger = {
            name: string
            label: string
            criteria?: string
            entity: string
            action: ('INSERT' | 'UPDATE' | 'DELETE')[]
            lookups?: BshTriggerLookup[]
            events: BshTriggerEvent[]
            enabled: boolean
            bshPlugin?: string
        }
        ```

        ### BshTriggerEvent Type

        ```ts
        export type BshTriggerEvent = {
            name: string
            function: string
            entity?: string
            criteria?: string
            input?: object
            output?: object
            failed?: object
            enabled: boolean
            infiniteLoop?: {
                maxDeep: number  // Default: 100
            }
        }
        ```

        ### Example: Creating a Trigger via API

        ```ts
        const trigger: BshTrigger = {
            name: "order-status-notification",
            label: "Send notification on order status change",
            entity: "Order",
            action: ["UPDATE"],
            enabled: true,
            criteria: "payload.status == 'SHIPPED'",
            lookups: [
                {
                    key: "customer",
                    search: {
                        entity: "Customer",
                        filters: [
                            {
                                field: "id",
                                operator: "eq",
                                value: "${payload.customerId}"
                            }
                        ],
                        fields: ["id", "email", "name"]
                    }
                }
            ],
            events: [
                {
                    name: "send-email",
                    function: "EmailSender",
                    enabled: true,
                    criteria: "lookups.customer.length > 0",
                    input: {
                        to: "${lookups.customer.0.email}",
                        orderId: "${payload.id}",
                        status: "${payload.status}"
                    },
                    output: {
                        emailSent: "$js(result.success)",
                        sentAt: "$js(new Date().toISOString())"
                    },
                    failed: {
                        error: "${error.message}",
                        orderId: "${payload.id}"
                    },
                    infiniteLoop: {
                        maxDeep: 50
                    }
                }
            ]
        }
        ```
